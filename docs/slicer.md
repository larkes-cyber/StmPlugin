# `agent/slicer.py` — переходник между агентом и STE Slicer

`slicer.py` — наш файл, не из исходников STE Slicer. Он содержит класс `SlicerAPI`: каждый его
публичный метод — это один инструмент агента (MCP-инструмент). Методы получают простые аргументы
(строки, числа, словари) и возвращают JSON-совместимые словари, а внутри вызывают штатный API слайсера:
`MachineManager`, `QualityManager`, `MaterialManager`, операции сцены Uranium, бэкенды, писатели
G-code и 3MF. Все вызовы сверены с исходниками `STE-Slicer-master` и `Uranium-steslicer`.

```
агент (LLM) / MCP-клиент
        │  tools.py: имя инструмента + аргументы
        ▼
SlicerAPI (slicer.py)  ── проверка аргументов, перевод координат, ожидание, логи, события для чата
        │
        ▼
STE Slicer: MachineManager, QualityManager, MaterialManager, сцена, CylindricalBackend, писатели
```

Если вызов не удался по понятной причине (нет модели, неверный ключ настройки, значение вне
диапазона), метод бросает `ToolError` с текстом на русском. Этот текст получают агент и пользователь.

## 1. Главное правило: потоки

Это самое важное, что нужно знать про файл. Почти все ошибки «слайсер завис» связаны с потоками.

| Поток | Кто там работает | Что можно делать |
|---|---|---|
| **Главный поток Qt** | интерфейс слайсера, сцена, настройки, OpenGL | всё, что трогает сцену, настройки и бэкенд |
| **Поток агента** (`AIAssistantAgent`) | цикл LLM ↔ инструменты | ждать, считать геометрию на numpy |
| **Поток HTTP** (`AIAssistantHTTP`) | чат и MCP-запросы | принимать запросы, вызывать инструменты |
| **Поток писателя** (`AIAssistantWriter`) | запись G-code и 3MF | вызывать писатели STE |

Как это устроено в коде:

- **`@on_main`.** Метод целиком выполняется в главном потоке: через `app.callLater` из `mainthread.py`
  вызывающий поток ждёт результат. Так помечены короткие методы: чтение и запись настроек, поворот,
  перемещение и т. д.
- **Методы без `@on_main`** — длительные: `load_model`, `start_slicing`, `arrange_all`, анализ
  геометрии, экспорт. Они запускают действие в главном потоке короткими вызовами `run_on_main(...)`,
  а **ждут результата в своём потоке**, чтобы интерфейс слайсера не замирал.
- **Писатели G-code и 3MF вызываются только из фонового потока.** В STE они помечены
  `@call_on_qt_thread` (`steslicer/Utils/Threading.py`). Этот декоратор *всегда* ставит работу в очередь
  главного потока и ждёт её. Если вызвать писатель из главного потока, тот будет ждать сам себя
  вечно: так зависал первый вариант плагина. Поэтому `_run_writer` запускает писатель в отдельном потоке
  с таймаутом, а при вызове из главного потока сразу отказывает.
- Если главный поток не ответил за 120 с, `run_on_main` пишет в `stderr.log` **стек главного потока**:
  видно, где он застрял.

## 2. Системы координат

В сцене Cura/STE ось **Y направлена вверх**, а передняя сторона стола соответствует **+Z** сцены.
Агенту и пользователю привычнее координаты стола, где Z смотрит вверх. `SlicerAPI` везде принимает
и возвращает **координаты стола**:

```
координаты стола (наружу)        сцена STE (внутри)
        x            ─────────►  x
        y            ─────────►  −z
        z (вверх)    ─────────►  y
```

- `PLATE_AXES_IN_SCENE` — оси для `rotate_object` (`"x"`, `"y"`, `"z"` стола → вектор в сцене).
- В `_node_info` центр объекта `center_mm` и размеры `size_mm` уже переведены в систему стола.
  `(0, 0)` — центр стола.
- Для геометрии треугольники переводятся функцией `geometry.scene_to_plate`, а оси поворота обратно —
  `geometry.plate_to_scene_vector` (подробнее в [geometry.md](geometry.md)).

## 3. Разделы файла

### 3.1. Константы и вспомогательные функции (вверху файла)

| Имя | Назначение |
|---|---|
| `PRINT_MODES` | допустимые режимы: `classic` (3D), `cylindrical` (5D Spiral), `cylindrical_full` (5D) |
| `PRINT_MODE_KEY` | ключ настройки режима — `printing_mode` (глобальная, из `fdmprinter.def.json`) |
| `MODE_LABELS` | человекочитаемые названия режимов |
| `MODEL_EXTENSIONS` | какие файлы принимает `load_model`: `.stl`, `.obj`, `.3mf` |
| `_app()` | экземпляр `SteSlicerApplication` |
| `_extruder_manager()` | `steslicer.Settings.ExtruderManager` |
| `_jsonable()` | приводит значения слайсера (numpy, OrderedDict, объекты) к JSON |
| `check_gcode(path)` | быстрая проверка G-code: строки, перемещения, слои `;LAYER:`, температуры, `;FLAVOR` |

> В определении `printing_mode` есть ещё `discrete`, `spherical`, `spherical_full`, но по условиям
> кейса используются только три режима из `PRINT_MODES`.

### 3.2. Настройки (`get_settings`, `search_settings`, `set_settings`, `reset_settings`)

Каждая настройка живёт в одном из двух стеков:

- **глобальный стек** (`getGlobalContainerStack()`) — общие настройки, в том числе `printing_mode`;
- **стек активного экструдера** — настройки с `settable_per_extruder = true` (температуры, скорости…).

`_stack_for(key)` сам выбирает нужный стек, поэтому агенту не нужно знать, где лежит ключ.

Как работает `set_settings(changes, reason)`:

1. `_require_key` — ключ существует? Если нет, агенту предлагается `search_settings`.
2. `_convert` — значение приводится к типу настройки:
   - `bool`: принимает `true/false`, `1/0`, «да»;
   - `int`, `float`;
   - `enum`: значение или подпись варианта, иначе ошибка со списком вариантов.
3. Проверка `minimum_value` / `maximum_value` из определения принтера (жёсткие границы).
4. Запись в `userChanges` нужного стека. Это тот же слой, куда пишет интерфейс, и он попадает в 3MF.
5. Обратное чтение фактического значения. В чат уходит событие `settings_changed` («было → стало» и причина).

Ошибочные ключи не прерывают остальные изменения: результат содержит `applied` и `errors`.
`validation_errors` — ключи, которые слайсер считает ошибочными (`getErrorKeys` обоих стеков).

`reset_settings(keys)` удаляет пользовательские изменения (все или по списку) и возвращает значения профиля.

### 3.3. Профили, материалы и режим печати

| Метод | Что вызывает в STE |
|---|---|
| `list_quality_profiles` | `QualityManager.getQualityGroups`, `getQualityChangesGroups` |
| `set_quality_profile(name)` | `MachineManager.setQualityGroupByQualityType` или `setQualityChangesGroup` |
| `list_materials(query)` | `MaterialManager.getAvailableMaterialsForMachineExtruder` |
| `set_material(material_id)` | `MachineManager.setMaterialById(position, root_material_id)` |
| `save_profile(name)` | `QualityManager.createQualityChanges(base_name)` |
| `get_print_mode` / `set_print_mode` | настройка `printing_mode` |

Агент выбирает профили и материалы **только из этих списков**: выдуманные id отклоняются.
Профиль с флагом `available = false` (не подходит к материалу или соплу) выбрать нельзя.

### 3.4. Сцена (`load_model`, `list_objects`, `move_object`, `rotate_object`, …)

- **ID объектов.** Узлам сцены присваиваются короткие ID `obj1`, `obj2`… (`_oid`). Если в сцене один
  объект, ID можно не указывать.
- **`load_model(path)`** вызывает `app.readLocalFile` и ждёт (до 120 с), пока в сцене появятся новые
  объекты и их число перестанет меняться (0.8 с). Возвращает ID и габариты новых объектов.
- **`rotate_object`, `scale_object`** вращают и масштабируют **вокруг центра модели**. В операциях
  Uranium по умолчанию центр — начало координат, поэтому точка задаётся явно. После этого модель
  возвращается на прежнее место по X/Y и опускается на стол (`_settle`).
- **Опускание на стол** делает штатная `GravityOperation` (`_drop_to_plate`). Она учитывает смещение
  по высоте (`getZOffset`), как в интерфейсе слайсера.
- **`arrange_all`** — штатная авторасстановка `app.arrangeAll()`. Она идёт фоновой задачей, поэтому
  метод ждёт 1.5 с перед ответом.
- **`delete_object("all")`** — штатный `app.deleteAll()`.
- Все изменения идут через операции Uranium (`TranslateOperation`, `RotateOperation`, …), поэтому
  их можно отменить в слайсере через Ctrl+Z.

### 3.5. Анализ геометрии

Чтение данных и расчёты разнесены по потокам:

1. `_prepare_geometry` (главный поток) собирает треугольники объекта в мировых координатах
   (`_plate_triangles`: сетка × матрица мировой трансформации, включая вложенные узлы) и переводит
   их в систему стола.
2. Расчёт идёт в потоке агента через функции [`geometry.py`](geometry.md), чтобы интерфейс не замирал
   на больших моделях.

| Метод | Что делает |
|---|---|
| `analyze_geometry` | габариты, объём, сетка, нависания, осесимметричность, подсказки |
| `suggest_orientations` | рейтинг ориентаций; варианты запоминаются для `apply_orientation` |
| `apply_orientation(rank \| down)` | поворачивает модель так, чтобы вектор `down` смотрел на стол |

Угол нависания по умолчанию берётся из настройки `support_angle` текущего профиля.

### 3.6. Снимок сцены (`get_scene_snapshot`)

Вызывает штатный `steslicer.Snapshot.snapshot()` — тот же рендер, что превью в G-code (изометрия:
камера спереди-слева-сверху). Рендер идёт через OpenGL, поэтому только в главном потоке.

PNG возвращается в поле `_image`. Дальше:
- `tools.py` показывает картинку в чате отдельной карточкой;
- `agent.py` отправляет её LLM следующим сообщением (в Chat Completions ответ инструмента — только текст);
- `mcp.py` отдаёт её MCP-клиентам блоком `image`.

### 3.7. Слайсинг

```
start_slicing ──► _start_slice (главный поток): подписка на сигналы бэкенда, forceSlice()
       │
       ▼  ждём в потоке агента (до 900 с), опрашивая self._slice["state"]
_on_backend_state / _on_progress  ◄── сигналы backendStateChange / processingProgress
       │
       ▼
done → _result_dict: время (PrintInformation.currentPrintTime), граммы и метры по экструдерам
```

- `_ensure_backend` подписывается на сигналы текущего бэкенда (`app.getBackend()`; в 5D это
  `CylindricalBackend`). Если бэкенд сменился, подписка переносится.
- Состояния `BackendState` переводятся в строки: `pending`, `processing`, `done`, `error`, `disabled`.
- Если бэкенд больше 5 с висит в `pending` (бывает, когда настройки поменялись во время слайсинга),
  слайсинг перезапускается, но не более двух раз.
- Прогресс уходит в чат шагами по 5 % (событие `slice_progress`).
- При ошибке в ответ добавляются `validation_errors`, чтобы агент понял, какие настройки мешают.

### 3.8. Экспорт (`export_gcode`, `save_project_3mf`, `export_results`)

| Метод | Писатель STE | Режим файла |
|---|---|---|
| `export_gcode` | `GCodeWriter` (плагин `GCodeWriter`) | текст |
| `save_project_3mf` | `ThreeMFWorkspaceWriter` (workspace_writer плагина `3MFWriter`) | бинарный |

Как идёт запись:

1. `_run_writer`: писатель получаем в главном потоке, вызываем в **отдельном потоке** с таймаутом 120 с (см. раздел 1).
2. `_write_atomic`: пишем в `файл.part` и переименовываем только при успехе, поэтому пустых или
   битых файлов не остаётся.
3. G-code сразу проверяется функцией `check_gcode`, результат уходит в чат.

**`export_results(model_name)`** собирает результат для сдачи:

```
<output_dir>/results/<model_name>/
├── result.gcode   ← пишется первым
└── project.3mf
```

G-code и 3MF пишутся независимо: если один не получился, второй всё равно сохранится, а ошибка
окажется в `errors`. Без `model_name` файлы попадают в `<output_dir>/latest/`. `output_dir`
задаётся в настройках чата (по умолчанию `Документы/STE_AI_results`).

## 4. События для чата

`SlicerAPI` сообщает чату о происходящем через `self._events.emit(...)`:

| Событие | Когда |
|---|---|
| `settings_changed` | изменены настройки или режим (с причиной) |
| `profile_changed` | выбран профиль или материал |
| `scene_changed` | загрузка, перемещение, поворот, масштаб, расстановка, удаление |
| `slice_state`, `slice_progress` | ход слайсинга |
| `snapshot` | снимок сцены |
| `file_saved` | сохранён G-code или 3MF (с результатом проверки) |

## 5. Как добавить новый инструмент

1. Добавьте метод в `SlicerAPI`. Если он короткий и трогает сцену или настройки, пометьте его
   `@on_main`. Если долгий, вызывайте слайсер через `run_on_main(...)`, а ждите в своём потоке.
2. Возвращайте словарь из простых типов (при необходимости через `_jsonable`). Ожидаемые ошибки
   сообщайте через `ToolError("понятный текст")`.
3. Зарегистрируйте инструмент в `build_registry` в `tools.py`: имя, описание для LLM, схема аргументов.
4. Если инструмент меняет сцену, отправьте событие (`scene_changed` и т. п.), чтобы обновилась
   боковая панель чата.
5. Добавьте метод с тем же именем в `dev/fake_slicer.py`, чтобы работали офлайн-тесты и демо.

## 6. Отладка

Все строки плагина в `stderr.log` начинаются с `AIAssistant:`. Для `slicer.py` полезно искать:

| Строка в логе | Что значит |
|---|---|
| `setting <ключ> [global/extruder]: старое -> новое` | изменение настройки |
| `setting <ключ> rejected: …` | значение отклонено проверкой |
| `loading model …` / `model loaded: …` | загрузка модели |
| `start slicing via CylindricalBackend.forceSlice` | какой бэкенд режет |
| `backend state: …` | переходы состояния слайсинга |
| `writing <путь> with 3MFWriter.ThreeMFWorkspaceWriter.ThreeMFWorkspaceWriter` | экспорт |
| `main thread timeout … Main thread is stuck here:` + стек | главный поток завис |
